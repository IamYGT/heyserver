# Heyserver Code of Conduct

Heyserver contributors and maintainers commit to a professional, welcoming, and
technically constructive project environment.

## Expected behavior

- Discuss the work, evidence, and trade-offs rather than attacking a person.
- Welcome questions and explain project-specific expectations without ridicule.
- Give actionable review feedback and acknowledge corrections.
- Respect different experience levels, identities, backgrounds, and viewpoints.
- Protect credentials, private reports, and real server data shared through an
  appropriate private channel.
- Disclose conflicts that could materially affect a project decision.

## Unacceptable behavior

- Harassment, threats, stalking, discriminatory language, or sexualized conduct.
- Personal insults, sustained disruption, or bad-faith review obstruction.
- Publishing another person's private information without permission.
- Deliberately exposing credentials, private vulnerability details, or user
  infrastructure data.
- Retaliation against someone who raises a good-faith conduct concern.

## Scope

This policy applies in Heyserver repositories, issues, pull requests, reviews,
release discussions, and project-run community spaces. It also applies when a
person officially represents Heyserver in another public space.

## Reporting a conduct concern

Do not put sensitive conduct details in a public issue, pull request, or support
form. Use the private contact route published on the [repository owner's GitHub
profile](https://github.com/IamYGT). Include only the minimum information needed
to identify the space, people involved, approximate time, and requested
follow-up. Do not attach credentials, private keys, or unrelated server data.

This route is for conduct concerns. Route other private reports as follows:

- **Vulnerability, suspected credential exposure, or Heyserver-caused security
  impact:** use the [private security advisory](https://github.com/IamYGT/heyserver/security/advisories/new)
  and follow [SECURITY.md](SECURITY.md); do not use a public issue.
- **Compromised host, lost credential, or outage:** isolate or recover the
  installation and rotate affected credentials first, then use the private
  security advisory if Heyserver caused or widened the impact.
- **Normal installation, usage, defect, feature, or integration help:** use the
  matching form in [SUPPORT.md](SUPPORT.md).

If the private security form is unavailable, use the repository owner's private
contact route and state that the report is security-sensitive; never disclose
security details in a public issue while waiting for a response.

## Review and enforcement

Maintainers will limit report access to people needed to evaluate it, give the
reported person a fair opportunity to respond when appropriate, and avoid
publicly identifying the reporter without consent. Depending on severity and
history, consequences may include a private warning, removal of content,
temporary participation limits, removal of project access, or a permanent ban.
The lead maintainer coordinates enforcement and resolves appeals. A maintainer
must recuse when personally involved; an uninvolved maintainer handles that
case and any appeal.

For an immediate threat, contact the appropriate local emergency or protective
service first. Project enforcement cannot replace local emergency response.
Exact project response times are not promised while Heyserver remains a small
pre-1.0 project, but good-faith reports will not be ignored or punished.

See [GOVERNANCE.md](GOVERNANCE.md) for role authority and the
[maintainer area map](MAINTAINERS.md) for responsibility coverage. The map names
roles, not personal identities; current access is determined by repository
permissions.
